# 写作风格与门禁规则

> 本文件是《大模型评估入门：从前端工程师视角看 Eval》一书的写作规范。
> 所有章节作者（含 AI 辅助）必须遵守。
> 违反门禁的章节不予合入。

---

## 1. 读者画像（不可越界）

**主读者：1-3 年前端工程师**
- 会 React / Vue / TypeScript，会写 Node.js，调过 OpenAI/Anthropic API
- **不懂** AI 训练术语（gradient / loss / tokenization / RLHF / SFT）
- 不读 arXiv 论文，看到公式会下意识跳过
- 想要：看懂厂商报告 + 自己能写评估

**次读者：5-8 年技术 Leader**（在第 13、19、20、21、22、23 章会显式出现）

### 1.1 越界红线（违反即返工）

| 越界 | 后果 |
| --- | --- |
| 假设读者懂 LoRA / SFT / RLHF | 退稿，必须先解释再使用 |
| 假设读者会 PyTorch / Python | 退稿，本书示例默认 TypeScript |
| 假设读者读过 MMLU 论文 | 退稿，本书给出原题 |
| 公式超过 3 行 LaTeX | 退稿，必须给口语化说明或拆解 |
| 直接引用论文段落而不翻译 | 退稿，必须中文翻译 + 关键术语括号 |
| 使用"显然" / "容易验证" / "trivial" | 退稿，必须展示步骤 |

## 2. 文风原则

### 2.1 一句话定位

> **以"给同事讲技术"的口吻写。** 不端着、不说教、不科普腔、不写综述。

### 2.2 类比优先

每个抽象概念**必须**先用前端工程师熟悉的类比解释。

| 抽象概念 | 必须用的类比（至少 1 个） |
| --- | --- |
| 评估 | 单元测试 / E2E 测试 |
| 基准（benchmark） | 测试套件（test suite） |
| 数据集 | 测试夹具（test fixture）|
| 评估指标 | 断言（assertion）|
| 评估流水线 | CI/CD 流水线 |
| 在线评估 | 生产监控（APM）|
| LLM-as-Judge | 代码审查（code review）|
| 人类评估 | 可用性测试 |
| 红队评估 | 渗透测试 |
| 评估覆盖率 | 测试覆盖率 |
| 评估的元评估 | 测试的可信度（测试自己是否可靠）|

### 2.3 训练术语词典

以下术语**第一次出现时必须解释**（用前端类比或一句话白话）：

| 术语 | 必须解释的话术模板 |
| --- | --- |
| Token | "模型看到的最小文本单位，类似前端的'字符'，但更碎——一个字可能被切成多个 token" |
| Tokenizer | "把文本切成 token 的工具，类似 Babel 把 JS 转 AST" |
| Gradient | "模型训练时的'纠错信号'，告诉你参数应该往哪个方向调；前端不需要这个概念，评估也不需要" |
| Loss / Loss Function | "训练时衡量模型输出离正确答案多远的分数，越小越好；评估时我们用类似但不同的指标" |
| RLHF | "用人类反馈训练模型，类似前端的'用户行为埋点 → 模型调整'，但评估环节不涉及" |
| SFT (Supervised Fine-Tuning) | "用标注数据再训练一轮；评估是检验这一轮效果的工具" |
| Pretrain | "模型先读海量文本打基础；评估是后续所有环节的'考试'" |
| Embedding | "把文本变成向量的过程，类似把字符串哈希成数字，但保留语义距离" |
| Prompt | "给模型的输入；评估里叫'被测输入'" |
| Completion | "模型的输出；评估里叫'被测输出'" |
| Hallucination | "模型一本正经地胡说八道；评估里专门有 hallucination 指标" |

### 2.4 严禁清单（永不出现）

| 严禁 | 替代 |
| --- | --- |
| "显而易见" / "显然" | 必须展示步骤 |
| "trivial" / "easy to verify" | 必须给出可执行验证步骤 |
| "众所周知" / "as we all know" | 必须给引文或链接 |
| "废话" / "会咬人" / "翻车" | 用"陷阱" / "失效" / "踩坑" |
| "弱智" / "是废的" | 严禁情绪化词 |
| 直接抄论文英文段落 | 中文翻译 + 关键术语括号 |
| "不要这样做" / "千万别" | 改为"这样做会怎样 → 应该这样" |
| "其实很简单" | 直接讲怎么做，不评价难度 |
| 把 React/Vue 贬低 | 我们是前端出身，尊敬前端 |

### 2.5 公式纪律

每个 LaTeX 公式**必须**配"在前端看来"的口语化说明。

**模板**：
```
$$公式$$

> 📝 **在前端看来**：这段公式相当于 [类比]。如果类比不出来，说明这个公式对你当前阶段不重要，跳过即可。
```

**允许的公式**（必须带类比）：
- 准确率 = 正确数 / 总数
- 精确率、召回率、F1
- BLEU / ROUGE（简化版）
- ELO 评分更新公式
- Cohen's Kappa

**不允许的公式**（用文字描述代替）：
- Loss 推导
- Attention 机制
- Transformer 架构
- 任何训练相关推导

## 3. 章节结构门禁

每章必须按以下结构组织，缺一项扣 30% 分：

### 3.1 章节模板（10 段式）

```markdown
# 第 N 章 [标题]

## 本章目标
[3-5 条可勾选的"读完能做什么"清单]

## 如果只读一节
[明确指出哪一节最关键]

## 为什么需要这一章
[200 字导读]

## N.1 [子节标题]
[内容]

## N.2 [子节标题]
[内容]

...

## N.M [子节标题]
[内容 + 代码示例]

## 本章小结
[3-5 句话总结]

## Try It（动手题）
- [ ] 题 1
- [ ] 题 2
- [ ] 题 3
- [ ] 题 4
- [ ] 题 5

## 验收自测
[5-10 道判断 / 选择 / 简答题]

## 延伸阅读
[3-5 条链接 + 1 句话推荐理由]

## 与其他章的关联
[用有向箭头标出 DAG 关系]
```

### 3.2 子节数量

- 每章 **5-7 个 H2 子节**（少于此过多，多于此过散）
- 每个子节 800-2000 字
- 每章总字数 5000-10000 字

### 3.3 代码示例

- 每章 **至少 1-2 个真实代码片段**
- 默认语言 **TypeScript / Node.js**（不写 Python，除非必须）
- 代码必须可运行（不是伪代码）
- 代码必须有注释（不是空白占位）
- 真实数据集样例（不改写、不缩写、不翻译）

### 3.4 表格纪律

- **厂商对比必用表格**
- **数据集对比必用表格**
- **框架对比必用表格**
- 表头要清晰，列数 ≤ 6
- 不写"X 比 Y 好"，写指标数值

### 3.5 标注纪律

每章必标：

| 标注 | 出现位置 | 例子 |
| --- | --- | --- |
| **如果只读一节** | 章节开头 | "如果只读一节，读 N.3 — 它是你读后续章节的钥匙" |
| **在前端看来** | 公式下方 | "在前端看来：这段公式就是 ... 的比例" |
| **陷阱** | 关键概念旁 | "⚠️ 陷阱：千万别把 X 当 Y 用" |
| **TL;DR** | 长段落首 | "TL;DR：这一段核心是 X" |
| **Try It** | 章节末尾 | 5 道动手题 |

## 4. 内容门禁

### 4.1 数据集样例真实性

- 必须给真实题目原文（MMLU 给 MMLU 原题，不改写）
- 必须标来源（论文 / GitHub 链接）
- 不改编、不缩写、不意译
- 中文题目（如 C-Eval）保留中文 + 出处

### 4.2 厂商对比表格化

每次提"X 模型 vs Y 模型"，必须用表格：

```markdown
| 模型 | MMLU | GPQA | HumanEval | 上下文 | 价格 |
| --- | --- | --- | --- | --- | --- |
| GPT-5 | 88% | 78% | 92% | 200K | $X/M |
| Claude 4 | 87% | 80% | 88% | 200K | $Y/M |
```

### 4.3 链接门禁

- 所有外部链接必须可访问
- 链接附带"为什么读"一句话
- arXiv 链接必须给编号（如 `arXiv:2501.12345`）

### 4.4 不确定声明规则

- "可能是" / "据我所知" / "似乎" 等模糊语 → 必须附引文
- 没用过的工具、没读过的论文 → 不得写评价
- 已知过时 → 必须标"截至 2026.08 已过时"

## 5. 风格基调（示例）

### 5.1 好的章节开头

```markdown
# 第 7 章 代码能力评估：HumanEval 到 SWE-bench

## 本章目标
读完本章你将能够：
- [ ] 解释 HumanEval 的一道函数题是怎么被自动评分的
- [ ] 解释 SWE-bench 是怎么让模型修一个真实 GitHub issue 的
- [ ] 在自己的代码生成项目里跑 LiveCodeBench 风格的子集评测
- [ ] 区分 HumanEval / MBPP / LiveCodeBench / SWE-bench 各自测的是什么

## 如果只读一节
读 7.3（SWE-bench）—— 这是当下厂商报告里最常出现的代码评估，不懂它就读不懂报告。
```

### 5.2 坏的章节开头（退稿示例）

```markdown
# 第 7 章 代码能力评估

代码能力评估是 LLM 评估领域的重要分支。近年来，随着大语言模型在代码生成任务上的表现不断提升，如何系统化地评估模型的代码能力成为研究热点。本章将介绍主流的代码评估基准...

（问题：套话、堆砌术语、没目标、没类比、没说读完能干嘛）
```

## 6. 发布门禁

### 6.1 每章合入前自检

作者提交章节前必须自查：

- [ ] 章节目标 3-5 条可勾选
- [ ] "如果只读一节"明确标注
- [ ] 5-7 个 H2 子节
- [ ] 每章 5000-10000 字
- [ ] 至少 1 段 TypeScript / Node.js 代码
- [ ] 真实数据集样例（不改写）
- [ ] 至少 1 个对比表格
- [ ] 所有训练术语首次出现已解释
- [ ] 所有公式配有"在前端看来"说明
- [ ] Try It 5 道动手题
- [ ] 验收自测 5-10 题
- [ ] 延伸阅读 3-5 条
- [ ] 与其他章的关联（DAG 箭头）

### 6.2 评审门禁（deep-tech-reviewer）

评审 Agent 必须检查：

- [ ] 是否有未解释的训练术语
- [ ] 公式是否有口语化说明
- [ ] 类比是否恰当
- [ ] 代码是否可运行（至少语法正确）
- [ ] 数据集样例是否真实
- [ ] 厂商对比是否公平
- [ ] 是否有空话 / 套话 / 黑话
- [ ] 是否越界（讲了 AI 训练内容）

### 6.3 不予合入的硬伤

- 没有"如果只读一节"标注
- 有超过 3 处未解释的训练术语
- 代码片段跑不通（语法错误）
- 厂商对比不中立
- 全章无类比
- 公式无口语化说明

## 7. 写作流程（每章）

```
1. 写章节目标（5 分钟）
2. 标"如果只读一节"（5 分钟）
3. 写每个子节（30-60 分钟/节）
   - 先写类比
   - 再写概念
   - 最后写代码
4. 写 Try It（30 分钟）
5. 写验收自测（30 分钟）
6. 自查 12 项门禁（15 分钟）
7. 提交 deep-tech-reviewer 评审
8. 修改 + 再审
9. 合入
```
