# 2. 评估的 5W1H：何时、何地、给谁、为什么评估

> **如果只读一节**：评估前先回答 6 个问题，80% 的无效评估死于没问清"为什么评估"和"评估什么"。

## 2.1 本章目标与读者

读完后你能：

- 用 5W1H 框架拆解一个评估需求
- 区分**离在线评估、参考/无参考评估、绝对/相对评估**
- 知道评估的 4 个时间点：训练前、训练中、训练后、上线后
- 理解"评估对象"不只是模型

**前置知识**：读完第 1 章。

## 2.2 5W1H 框架

| 维度 | 问题 | 错误答案 | 正确答案样例 |
|---|---|---|---|
| **Why** | 为什么评估 | "老板让做" | "我们要在 3 个候选模型里选一个做客服" |
| **What** | 评估什么 | "模型好不好" | "模型回答用户退款问题的准确率" |
| **Who** | 谁来评估 | "我" | "我 + 5 个客服专家 + 100 个真实用户" |
| **When** | 何时评估 | "上线前" | "训练中每 N 步 + 上线后持续" |
| **Where** | 在哪评估 | "本地笔记本" | "和线上同样配置的 GPU + 同 prompt 模板" |
| **How** | 怎么评估 | "跑分" | "200 道客服场景 + 准确率 + 延迟 + 满意度" |

**这 6 个问题没问清就开始跑评估 = 100% 浪费时间。**

## 2.3 评估的 4 个时间点

```
1. 训练前（Pre-training eval）
   → 基线模型在 5 个公开基准上的分数

2. 训练中（Mid-training eval / SFT/RLHF）
   → 每 1000 步跑一次小规模评测，看 loss 下降时 eval 是否提升

3. 训练后（Post-training eval）
   → 完整测试集，决定是否发布

4. 上线后（Production eval / Online eval）
   → 用户反馈、点赞率、人工抽检、A/B 实验
```

**前端类比**：

| 时间点 | 前端类比 | 评估对象 |
|---|---|---|
| 训练前 | 选框架前的 demo | 模型架构 |
| 训练中 | TDD 开发 | 训练步数 |
| 训练后 | 集成测试 | 发布版本 |
| 上线后 | 线上监控 + 错误日志 | 用户实际体验 |

**90% 的 AI 团队只做时间点 3，忽略 1、2、4。这是上线后翻车的主因。**

## 2.4 评估的 3 种分类法

### 分类 1：离线 vs 在线

| 离线（Offline） | 在线（Online） |
|---|---|
| 跑固定数据集 | 真实用户请求 |
| 分数可复现 | 持续波动 |
| 便宜、可控 | 真实但贵 |
| 适合回归、选型 | 适合监控、A/B |

### 分类 2：有参考答案 vs 无参考答案

| 有参考答案（Reference-based） | 无参考答案（Reference-free） |
|---|---|
| 准确率、BLEU、pass@k | LLM-as-Judge、人类偏好、Arena Elo |
| 题目答案固定 | 答案开放 |
| 适用：MMLU、GSM8K、HumanEval | 适用：写作、对话、Agent 任务 |

### 分类 3：绝对 vs 相对

| 绝对评估 | 相对评估 |
|---|---|
| 模型 X 在 MMLU 上 85% | 模型 X vs 模型 Y 哪个更好 |
| 数字直接可比 | 通常用 Elo 分数或胜率 |
| Chatbot Arena、MT-Bench | 偏好类基准 |

## 2.5 评估对象不只是模型

很多团队只评估"模型本身"，但实际影响业务的还有 5 层：

```
[1] 基础模型 (Base Model)
    GPT-4o, Claude 3.5, Qwen2.5-72B, DeepSeek-V3
    ↓
[2] 提示词 (Prompt / System Message)
    "你是一个耐心的客服..."
    ↓
[3] 上下文 (Context / RAG)
    检索回来的 5 段文档
    ↓
[4] 工具 (Tools)
    函数调用的 schema
    ↓
[5] 编排 (Orchestration)
    多次调用的链路、错误处理
```

**任何一层变化都要重新评估。** 改一个 prompt 词，可能比换模型影响更大。

## 2.6 评估的"最小必要"决策树

```
问：你有真实用户吗？
├─ 是 → 在线评估为主，离线为辅
└─ 否
   │
   问：你的任务有标准答案吗？
   ├─ 是 → 用 reference-based 基准（MMLU/GSM8K/HumanEval 风格）
   └─ 否
      │
      问：你能请到领域专家吗？
      ├─ 是 → 人类评估为主，LLM-as-Judge 辅助
      └─ 否 → LLM-as-Judge + 多模型投票
```

## 2.7 实战与陷阱

### 陷阱 1：评估"了"但没"用"

```
跑了 10 个基准 → 写报告 → 归档 → 模型还是凭感觉选
```

**对策**：评估报告必须含 1 个明确决策（"基于 X 基准 Y 分，我们选模型 A"）。

### 陷阱 2：评估数据集太小

100 道题的"准确率 90%"vs 1000 道题的"准确率 90%"，前者误差可能 ±5%。

**最小样本量经验法则**：
- 准确率类：≥ 500 道题
- 偏好类（Arena）：≥ 5000 次投票
- 开放式（写作）：≥ 200 条 + 多个评分员

### 陷阱 3：评估集和实际分布不一致

```
评估集：英文 Wikipedia 风格
真实场景：中文客服对话
准确率差距：可能 20%+
```

**对策**：在真实用户样本上**至少**留 20% 作为 hold-out。

## 2.8 评估的组织流程（企业级）

```
[需求方提出业务目标]
       ↓
[AI 团队拆解为能力维度]
  - 知识覆盖
  - 推理能力
  - 工具使用
  - 安全合规
       ↓
[选定或构建数据集]
  - 公开基准 + 业务定制
       ↓
[设计指标]
  - 准确率 + 延迟 + 成本 + 满意度
       ↓
[选择评分方式]
  - 自动 / LLM-as-Judge / 人类
       ↓
[跑评估 + 出报告]
  - 数字 + 错误样例 + 改进建议
       ↓
[决策：选型/发布/回滚]
```

**第一步"拆解能力维度"是最常被跳过的。** 没有这步，评估就是"凭感觉打分"。
