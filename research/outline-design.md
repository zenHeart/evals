# 《大模型评估入门：从前端工程师视角看 Eval》设计思路

> 本文件是这本书的"设计图纸"。先回答三个问题：
> 1. 这本书为谁而写？(读者画像)
> 2. 为什么他们会打开这本书，又为什么他们会读完？(价值主张与痛点)
> 3. 为什么是这个目录结构而不是另一个？(结构论证)

> 写给作者自己、写给评审者、写给未来要扩展这本书的人。

| 维度 | 状态 |

- **不写给学术研究者**：本书刻意避开文献综述与论文回顾

## 2. 痛点论证：为什么阿辰需要这本书

### 2.1 三种典型"评估焦虑"

| 焦虑场景 | 现状 | 本书如何缓解 |
| --- | --- | --- |
| **场景 A：报告看不懂** | GPT-5 / Claude / Gemini 报告里一堆缩写（MMLU、GPQA、AIME、HumanEval）看不懂，不知道数字含义 | 第 5–9 章按"能力家族"逐个拆解，每个评估都讲清"它测什么 / 它怎么测 / 为什么这个数字重要" |
| **场景 B：我的应用怎么评** | 做了 RAG demo，效果自己感觉不错，但老板问"准确率多少"答不上来 | 第 19–22 章提供从业务目标到评估流水线的完整方法论 |
| **场景 C：评估框架选哪个** | 听说有 lm-eval-harness、OpenCompass、Promptfoo、RAGAS、DeepEval 一堆框架，不知道选哪个 | 第 13 章按"通用能力 vs 应用层评估"分类，提供选型决策树 |

### 2.2 三个"我已经懂 X 但评估那部分我不懂"的真实对话

> **对话 1**（来自某前端技术分享会）：
> "我看 GPT-5 技术报告里 MMLU 拿了 88%，SWE-bench 拿了 75%。这两个数字我能背，但它们到底是怎么测的？75% 的 SWE-bench 是说 GPT-5 能修 75% 的 GitHub issue？"
> — *本书第 7 章 SWE-bench 节回答了这个问题，给你看一个真实的 GitHub issue 例子*

> **对话 2**（来自某 RAG 项目周会）：
> "我们的 RAG 看着挺好，但怎么量化？'看着挺好'不算评估。"
> "要不看看 RAGAS？"
> "RAGAS 是啥？metrics 又有一堆……"
> — *本书第 17 章 RAGAS 节直接给一段 30 行 Node.js 代码，能在你的数据上跑出来*

> **对话 3**（来自某团队技术评审）：
> "我们的 Chatbot Arena ELO 是 1280，对手是 1250，我们比对手强。"
> "可人家那个 1250 是开源 70B 模型，我们是闭源 API，模型规模都不一样。"
> — *本书第 10 章回答了 ELO 怎么算、什么情况下能比、什么情况下不能比*

## 3. 核心方法论：把"评估"类比为前端工程师熟悉的东西

### 3.1 一句话类比

> **LLM 评估 ≈ 单元测试 + E2E 测试 + 性能监控 + A/B 实验**

| 前端概念 | 评估对应 | 章节 |
| --- | --- | --- |
| 单元测试 | 单题测试（HumanEval 一道函数题）| 第 7、13 章 |
| 集成测试 | 基准测试（MMLU 多领域多题型）| 第 5、13 章 |
| E2E 测试 | 应用层评估（RAG 端到端评估）| 第 17 章 |
| 性能监控 | 在线评估与 A/B 实验 | 第 22 章 |
| 测试覆盖率 | 评估覆盖度（能力家族覆盖度）| 第 9、23 章 |
| 测试金字塔 | 评估金字塔（基础 → 偏好 → 应用）| 第 3 章 |
| CI/CD | 评估流水线 | 第 21 章 |

### 3.2 "为什么用单元测试这个类比"

- 前端工程师对测试金字塔天然有感觉
- 单元测试隔离、断言、可重复的特性，与 LLM 单题评估完全对得上
- 单题评估的"输入 → 期望输出 → 评分"三元组与单元测试的"输入 → 期望值 → 断言"完全同构
- 第一次讲解"什么是评估"时直接给一段 Jest/Vitest 代码，把 LLM 评估的骨架画出来

## 4. 结构论证：为什么是 6 部分 28 章

### 4.1 顶层设计原则

**原则 1：先建立心智模型，再看工具，最后做项目**
- 第 1–4 章：世界观与方法论（Why & What）
- 第 5–12 章：评估对象家族图谱（What to evaluate）
- 第 13–18 章：评估工具与工程（How to evaluate）
- 第 19–23 章：自定义评估设计（How to design for YOUR app）
- 第 24–28 章：实战与收口

**原则 2：每一部分都遵循"是什么 → 怎么用 → 怎么造"**
- 任何概念都从"它是什么"开始，到"怎么自己实现一个简化版"结束
- 这样 1-3 年工程师读完能立刻动手，不是"看完忘"

**原则 3：避免"百科全书"陷阱**
- 不写 MMLU 论文的历史、ARC 的引用数、作者八卦
- 只写"前端工程师要用这个评估时必须知道的 5 件事"

### 4.2 章节数量论证

| 部分 | 章数 | 论证 |
| --- | --- | --- |
| 第 1 部分：世界观 | 4 章 | 心智模型必须有，否则后面读不懂；超过 5 章会拖节奏 |
| 第 2 部分：基准家族 | 5 章 | 5 大能力家族（知识/数学/代码/多模态/其他）；每个 1 章，每章 4-8 个评测 |
| 第 3 部分：偏好生态 | 3 章 | 偏好 + 报告解读 + 排行榜；3 章足矣，再多就重复 |
| 第 4 部分：工程实践 | 6 章 | 这是工程书的主战场，必须够厚：框架 → 自建 → LLM-as-Judge → 人类评估 → RAG/Agent → 安全 |
| 第 5 部分：自定义设计 | 5 章 | 全书最关键（用户核心需求）：目标 → 测试集 → 流水线 → 在线 → 元评估 |
| 第 6 部分：实战收口 | 5 章 | 3 个完整案例 + 资源 + 自测 |

### 4.3 章节内"30% 概念 + 50% 实操 + 20% 陷阱"分配

每章内容按以下比例分配：
- **30% 概念铺垫**：用前端类比讲清楚这是什么
- **50% 实操代码 / 真实示例 / 跑得通的代码片段**
- **20% 常见陷阱 / 反例 / "我同事踩过的坑"**

## 5. 阅读路径：3 轮阅读法

### 5.1 第一轮（2 天）：建立全景（建议路线：第 1、2、3、5、13、19 章）

- **目标**：建立"评估是什么 + 主流评估长什么样 + 我能不能自己写一个"
- **跳过**：第 6–12、14–18、20–23、24–28 章细节
- **产出**：能在 30 分钟内给别人讲清楚"评估"是什么

### 5.2 第二轮（1 周）：按工作场景深读

根据阿辰的工作内容选一条路径：

| 工作场景 | 推荐路径 |
| --- | --- |
| 我在做 Chatbot | 第 4 → 第 10 → 第 13 → 第 15 → 第 17 → 第 19 → 第 24 |
| 我在做代码生成 / Agent | 第 4 → 第 7 → 第 13 → 第 15 → 第 17 → 第 19 → 第 25 |
| 我在做多模态 / 图像 | 第 4 → 第 8 → 第 13 → 第 15 → 第 17 → 第 26 |
| 我是 Leader，要建立团队规范 | 第 4 → 第 13 → 第 18 → 第 19 → 第 20 → 第 21 → 第 22 → 第 23 |

### 5.3 第三轮（长期）：当作参考手册

- 工具书 / Cheat Sheet 形态
- 第 11 章（读厂商报告）随时翻
- 第 12 章（第三方排行榜）随时翻
- 第 13 章（框架全景）选型时翻
- 第 27 章（术语表）当字典翻

### 5.4 第四轮（可选）：案例研究

- 读完正文后挑 1-2 个案例研究跟做（24、25、26 任选）
- 在自己的项目里跑一遍完整评估流水线

## 7. EPUB 与 Web 双形态发布策略

### 7.1 为什么是双形态

| 形态 | 适用场景 | 技术实现 |
| --- | --- | --- |
| **VitePress Web** | 在线阅读、搜索、可点击链接、代码可复制 | VitePress + Vue 3 |
| **EPUB3** | 离线阅读、Kindle / iBooks / Android 阅读器 | pandoc + 自定义 CSS |

### 7.2 内容形态差异

| 元素 | Web | EPUB |
| --- | --- | --- |
| 代码块语法高亮 | ✅ Shiki | ✅ 静态着色 |
| Mermaid 图表 | ✅ 渲染 | ⚠️ 转换为静态图片 |
| 可点击外部链接 | ✅ | ✅（但需要 rel 标记）|
| 真实数据集样例 | ✅ JSON / 文件下载 | ⚠️ 截屏 + 文字 |
| 搜索 | ✅ | ⚠️ 全文检索有限 |
| 习题答案 | ✅ 可隐藏/展开 | ✅ 内嵌 |
| 章节导航 | ✅ 左侧目录 | ✅ 章节导航 |

### 7.3 发布流水线

```
Markdown 源 (book/chapters/*.md)
    │
    ├── VitePress → github pages (Web 版)
    │
    └── pandoc → EPUB3 → ePubCheck → 发布
```

### 7.4 版本同步规则

- 同一份 Markdown 源文件双形态输出
- Web 是首选（最新内容更新 24 小时内可见）
- EPUB 每月发布一次稳定版（每月 1 号）
- 修订通过 Git tag 标记（如 `v2026.09.01`）

## 8. 风险与权衡

### 8.1 内容会过时

LLM 评估领域每个季度都有新基准出现。本书**不追新**，而是**抓共性**：
- 不写"2026 年最新评估"
- 写"评估的永恒模式：数据 → 推理 → 评分 → 报告"

### 8.2 数学公式门槛

不可避免会涉及一些公式（如准确率 = 正确数 / 总数、BLEU 公式）。处理方式：
- 公式必须配 LaTeX
- 公式下方必须配"在前端看来"的口语解释
- 数学符号第一次出现时必须用文字定义

### 8.3 不踩厂商

每个厂商都会被提及与对比。处理方式：
- 厂商对比必须用统一表格
- 不偏袒任何厂商
- 强调"用哪个看你的场景"

### 8.4 不重复造框架

第 13 章评测框架全景时，**不写**如何使用每一个框架的细节。处理方式：
- 只写"它是哪个能力域的标准选择"
- 链接到官方文档
- 本书**示范** lm-eval-harness 与 Promptfoo 两个最有代表性的

## 9. 写作风格门禁（详见 `book/AGENTS.md`）

| 门禁 | 说明 |
| --- | --- |
| 前端类比优先 | 每个抽象概念先找前端类比，再用 AI 术语 |
| 训练术语零容忍 | gradient / loss / tokenization / RLHF 第一次必须解释 |
| LaTeX 必配口语 | 公式下方必须有"在前端看来"说明 |
| Try It 收尾 | 每章结尾 3-5 个动手题 |
| 真实数据集原文 | 不改写、不缩写、不翻译 |
| 厂商对比表格化 | 不写"X 比 Y 好"，写表格行 |
| 一节标注 | 必标"如果只读一节" |
