## 二、根因：worker 阶段已结束，「停滞」信号是阶段切换的伪阳性

`conductor.sh` 的停滞判据是「accepted 3 小时不涨 **且** evidence 目录 3 小时无新写入」。这两条在 worker 阶段结束后会**同时**恒成立：

- 02:01:45 `[auto] worker=pass 489/fail 6/skip 12 · gate=accept 413/reject 75 · queue 0 · slots x=0 glm=0 old=0` —— 全部 worker 交卷；
- 02:01:46 `[auto] ALL WORKERS DONE → finalize` —— `monitor2.sh` 走收口分支，keeper 按设计退出；
- 之后 `accepted` 只可能因为发布器复验（regate）而变化，不可能再增长；`evidence/` 只由 worker 写，worker 没了自然停写。

即：**没有页面可再 accept，也没有 worker 可再写证据**。此时重启 worker / keeper 是错的——`keeper2.sh` 在 `q=0 && x=0` 时立即退出，重启只会空转甚至按 `seq 1 7` 拉起 7 个进程后立刻退出。

## 三、本轮修掉的 3 个真实缺陷

### 缺陷 1：`economically-important-tasks` 的 `status` 是非法枚举值 → 发布门禁必败

`out/economically-important-tasks.json` 的 `status` 被写成自由文本 `"内部评测，公开后继为 GDPval"`，而 `scripts/validate-data.mjs:33` 的 `benchmark_status` 只允许
`active / rolling / near-saturation / historical / superseded / deprecated`（另允许 `null`）。

后果：05:09 起 3 次门禁全部 `rc=20 · validate-data FAIL`，07:05:13 被记入 `publish-blocked.tsv` 隔离；worker 阶段已结束，没有人会再改写这个 out 文件，**这一页会永久停在隔离区**。

修复：改为 `superseded`。依据是该页自证文本——`summary`：「七周后 OpenAI 把这条评测线公开化成 GDPval」，`notes`：「与 gdpval 同叙事线但题集不同源」；`full_name` 仍保留「OpenAI 内部…评测（官方未命名）」，「内部评测」这个事实没有丢，只是从枚举字段移到本就承载它的字段。全仓扫描确认这是 485 个 out 文件中唯一一处枚举越界。

修复后实测：发布器自动检出 out 变化 → 解禁 → 重新验收 `accept（check_err=0 quotes=27 fresh_found=27 fresh_missing=0）` → **07:23:41 上线成功**。

### 缺陷 2：`jointavbench` 的 `profile.sources` 是 dict 不是数组 → `check-one.mjs` 直接崩溃

`out/jointavbench.json` 的 `profile.sources` 被写成以来源 id 为键的对象，而规范（`scripts/benchmark-profile.mjs:47` `checkSources`）要求 `sources` 为**非空数组**，每项含 kebab-case `id` / 合法 `kind` / `title` / HTTPS `url` / ISO `accessed`。

后果不是「校验不过」而是**进程崩溃**：

```
TypeError: object is not iterable (cannot read property Symbol(Symbol.iterator))
    at checkSources (…/benchmark-profile.mjs:49:21)
    at validateProfile (…/benchmark-profile.mjs:69:50)
    at file:///workspace/rollout/check-one.mjs:11:19
```

`gate.sh` 用 `c=$(node check-one.mjs … | head -1)` 取第一行，崩溃时 `c` 为空串 → `json.loads("")` 抛异常 → `$verdict` 为空 → **只往 `gate.tsv` 追加一行空判定**。所以 `jointavbench` 从 11-13 22:20 到 11-16 02:01 被 gate 了 30 次，30 行全是空判定，既拿不到 accept 也拿不到 reject，**永远不可能进候选、不可能发布**，而且每轮 gate 都白跑一遍。

修复：按 `sources[]` 规范把 5 个来源（`arxiv-2512-12772` / `hf-jointavbench` / `hf-roverx` / `github-jointavbench` / `project-page`）转成数组，原键名作 `id`，`kind/title/url/accessed/note` 全部原样保留（信息无损；`diff` 只有 19 行，全是括号与 `id` 键）。

修复后实测：`check-one.mjs` → `{"id":"jointavbench","cites":38,"quotes_ok":80,"quotes_bad":0,"errors":0}`；重启的 `monitor2.sh` 首轮 `gate.sh` 于 07:07:49 判 **accept（check_err=0 quotes=80 fresh_found=80 fresh_missing=0 unverified=0 unfetch=0）**，`gate accept` 413 → **414**，且已进入可发布候选（`need=0`）。

### 缺陷 3：`finalize.sh` 的 90 分钟超时相对发布 backlog 太短 → 会误打 `READY_FINAL`

`finalize.sh` 用墙钟等待发布器排空：`MAXWAIT=${FINALIZE_MAX_WAIT:-5400}`（90 分钟）。但当前待发布是 264 页、约 8–9 小时的量级。超时后它会无条件 `touch READY_FINAL`，而 `READY_FINAL` 一出现就有两条连带伤害：

1. `publisher.sh` 主循环里 `FRESH` 一旦短暂为空（典型：剩下 41 页都在 STALE 等复验）就 `echo drained` 并 `if [ -f READY_FINAL ] → exit 0` —— **带着几百页没发完就退出**；
2. `conductor.sh` 的发布器守护被 `[ ! -f $R/READY_FINAL ]` 挡死，不会把它拉起来，同时会提前启动 `taskB`（最终收尾，跑在 `/workspace/evals-publish`，与发布器争同一个 main）；`ext-queue/dispatcher.sh` 的 `qa_ready()` 也会放行 EXT-QA。

修复：终止滞留的 `finalize.sh`（它只写 `READY_FINAL` 和 `progress.md`，不碰任何页面数据），按 `monitor2.sh` 的既有链路以 `FINALIZE_MAX_WAIT=172800`（48 小时）重启 `monitor2.sh`，让 `READY_FINAL` 只在发布器**真正排空**后出现。实测新 `finalize.sh` 已继承该环境变量并在 `state=running 0s` 处正常等待。
